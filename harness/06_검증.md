# 검증

## 부분 검증 (검증 세션, 대상마다 /new)
```
검증 세션이다. clean을 검증해.
contract.md의 clean 부분, rules.json, `git log --oneline`의 [clean] 커밋, work_src/clean만 본다.
1. 테스트를 실행하고, 결과가 contract의 필드 뜻대로인지 원본 몇 행과 직접 대조해.
2. 입력 건수 = 결과 건수 + 버린 건수 + 확인 필요 건수인지 확인해.
3. 결과 JSON이 다음 부분의 입력 형식과 이어지는지 확인해.
지적은 verify.md에 'clean 지적 N'으로 근거(파일·줄·데이터 행)와 함께 써. 앞선 결론을 지지하지 말고 틀린 곳을 찾아. 파일은 고치지 마.
```
- 지적은 계획 세션에서 처리를 정한다 → DECISIONS.md: `clean 지적 2 거절: 이유`
- 고치는 일은 해당 구현 세션: "verify.md의 clean 지적 1, 3을 반영해"
- 모든 부분을 검증할 필요는 없다. 판정·배정·정리처럼 틀리면 결과가 바뀌는 부분만

## 통합 검증 (구현 세션이 모두 끝난 뒤)
```
검증 세션이다. 통합 검증
```
- 검증 세션이 `work_wiki/scenarios.md`에 시나리오 목록(S1, S2…)을 먼저 쓰고, 하나씩 실제로 실행해 결과(통과 / 실패 / 확인 필요)를 채운다
- 시나리오 출처: README 페르소나 기능, facts.md의 손실·목적·성공 기준, 상태 표의 경로, 운영 조건 변경 후 다시 생성, 권한, 데이터 함정, AI 실패, SOLUTION.md·Docker 실행
- 부분 사이 연결(앞 부분 결과 건수 = 뒷 부분 입력 건수, 같은 필드 같은 뜻)도 이때 함께 본다
- 실패·확인 필요는 verify.md에 `통합 지적 N` → 계획 세션에서 처리 결정 → 해당 구현 세션이 고침
- '담당자 확인 필요' 시나리오는 인터뷰 세션으로 넘긴다:
  ```
  인터뷰 세션이다. 질문 목록 갱신. scenarios.md의 담당자 확인 필요 시나리오를 결과 확인 질문으로 만들어.
  ```
  → questions.md '결과 확인'에 보여 줄 순서와 물어볼 문장이 생긴다 (손실이 해결된 장면 → 기준 바꿔 다시 만들기 → 사용자 화면 → 남은 한계)

## UX 검증 (서비스 완성 후, ux-ui-audit-hackathon 스킬)
```
UX 검증 세션이다. ux-ui-audit-hackathon 스킬로 검수해. 시험용 계정은 SOLUTION.md에 있어.
```
1. UX 시나리오 5~8개를 먼저 만든다 (사용자, 하려는 일, 시작 화면, 단계, 성공 조건, 지켜볼 것). 손실마다 "그 손실을 화면으로 막는 장면"이 하나씩 들어가야 한다
2. 시나리오마다 단계 파일을 만들어 `walk.mjs`로 따라 한다 → 끝까지 진행 / N단계에서 막힘, 스크린샷
3. 거친 화면을 `audit.mjs`로 측정한다 (로그인 상태 파일 사용)
4. `work_wiki/ux_audit.md`: 시나리오 표와 결과 → Issue(관련 시나리오 번호) → 구현 세션에 넘길 지시문
5. 내가 Critical·High 중에서 고칠 것을 골라, 보고서 끝 지시문을 화면 구현 세션에 붙여 넣는다
6. 고친 뒤 `UX 검증 세션이다. 재검증` → 같은 시나리오로 다시 따라 하고 '반영 결과'를 채운다
- 통합 검증(scenarios.md)은 기능이 맞는지, UX 검증(ux_audit.md)은 사용자가 헤매지 않고 잘못 판단하지 않는지를 본다. 겹치는 시나리오는 번호로 서로 가리킨다

## 전체 감사 (제출 30분 전)
```
검증 세션이다. 결과물 전체를 감사해. 아래 관점에서 틀렸을 수 있는 곳을 찾아 verify.md에 'final 지적 N'으로 써.
1. 빈 값·실패·0이 같은 것으로 처리된 곳
2. 정규화·병합으로 서로 다른 것이 하나로 합쳐진 곳
3. 단위·범위·날짜 기준이 다른 값을 비교한 곳
4. 화면·문서의 결론이 코드·데이터보다 강하게 말하는 곳
5. 문서에 있는데 코드에 없는 기능, 테스트가 확인하지 않는 주장
6. rules.json을 안 읽고 코드에 숫자가 박힌 곳, 근거 없는 운영 조건
치명/중요/경미로 나누고, 확신 없는 것은 '확인 필요'. 파일은 고치지 마.
```

## 사람이 직접 할 것
- 담당자에게 결과 보여 주기: 화면을 말로 설명하고 "이상한 점 있나요?" → 답을 인터뷰 세션에 붙여 넣기 → 하나 고치고 커밋
- 사용자 경로: 브라우저 미리보기에서 처음부터 사용자처럼 써 보기 (역할이 둘이면 둘 다)
- AI 실패 확인: API 주소를 일부러 틀리게 해서 대체 결과와 라벨이 나오는지
- 원본 대조: 결과 숫자 한두 개를 원본 파일에서 직접 세어 보기
- 문서 대조: SOLUTION.md의 명령을 그대로 실행해 보기

## 체크
- [ ] 테스트를 실제로 실행했다 (세션 기록에 결과가 남음)
- [ ] 깨진 입력에서 추측으로 채우지 않는다
- [ ] 부분마다 처리 전후 건수, 버려진·연결 안 된 건수가 보인다
- [ ] 운영 조건을 바꾸면 결과가 바뀐다
- [ ] 서버가 0.0.0.0에 바인딩된다
- [ ] 민감 정보가 화면·문서·커밋에 없다
- [ ] `git status`에 남은 변경이 없다 (검증·진행상황 정리 세션이 파일을 고치지 않았다)
