# 인터뷰: 세 질문 전략

과제 설명은 일부러 모호하다. 좁히는 과정 자체가 평가된다.
질문은 한 번에 하나. 해결책을 먼저 말하지 않는다. "할 일을 정리해 달라"는 통하지 않는다.

## 순서
현재 방식 → **손실** → (해결책이 나오면) **목적** → 숫자·경계 → **빠진 것** → 요약 확인

## 0. 현재 방식
- "지금은 이 일을 어떻게 하세요? 하루에 몇 번, 얼마나 걸려요?"
- "임시로 쓰는 방법(엑셀, 번역기 등)이 있나요?"
- "이걸 누가, 언제, 어떤 상황에서 해요?" → 사용자를 '회사'가 아니라 '그 결정을 하는 한 사람'으로

## 1. 손실 묻기 — 왜 지금 풀어야 하나
- 언제: 현재 방식을 들은 직후, "시간이 오래 걸려요" 같은 표면 불만이 나왔을 때
- 질문
  1. "안 고치면 어떤 일이 생겨요?"
  2. "최근에 실제로 문제가 된 적이 있나요? 그때 어떻게 됐어요?"
  3. "그때 얼마나 손해였어요? (건수, 금액, 시간)"
  4. "이게 잘 처리됐던 날도 있었어요? 그날은 뭐가 달랐어요?" (원인 좁히기)
- 들을 신호: 날짜가 있는 사건, 숫자, 다른 사람·고객의 피해
- 주의: "불편하다, 번거롭다"에서 멈추면 아직 표면. 사건 하나가 나올 때까지 질문을 바꿔 다시 ("지난달에 제일 곤란했던 날은요?"). "왜 놓치셨어요?"처럼 탓하는 질문은 피한다.

## 2. 목적 묻기 — 요청 뒤의 진짜 필요
- 언제: 실무자가 기능이나 해결책을 말할 때 ("AI로 써 주세요", "대시보드가 있으면")
- 질문
  1. "그게 생기면 무엇을 하시려고요?"
  2. "그 결과를 누가, 언제, 어떤 결정에 써요?"
  3. "그게 잘 되면 결국 무엇이 좋아져요?" (목표를 한 단계 올리기)
  4. "지금 이 판단을 할 때 누구 말이나 어떤 자료를 믿으세요?" (신뢰의 출처)
- 들을 신호: 사람과 시점("매일 아침 회의 전에"), 결정("어느 걸 먼저 처리할지")
- 주의: 실무자가 말한 해결책을 바로 받아 적지 않는다.

## 3. 숫자·경계
- "어떻게 되면 성공이라고 보세요? 지금은 얼마예요?"
- "기준을 정한다면 몇이 적당할까요? (예: 몇 초, 몇 건)" → 가정값으로 기록
- "이건 누가 최종 결정해요?" (사람 승인)
- "외부로 나가면 안 되는 정보가 있나요?" (보안·개인정보)

## 4. 빠진 것 묻기 — 숨은 조건
- 언제: 요약 확인 바로 전
- 질문
  1. "제가 아직 안 여쭤봤는데 중요한 게 있을까요?"
  2. "이걸 만들면 곤란해질 사람이나 상황이 있을까요?" (범주를 바꿔 묻기)
  3. "이번에 없어도 되는 건 뭐예요?"
- 들을 신호: 보안 지침, 사람이 결정할 일, 예외 데이터, 범위 밖 요구
- 주의: 실무자는 묻지 않은 핵심을 먼저 말하지 않는다. 범주를 바꿔서 물어야 나온다.

## 5. 요약 확인 문장
"제가 이해한 건, ○○(사람)가 ○○(상황)에서 ○○(표면 문제)가 아니라 ○○(진짜 문제) 때문에 ○○(손실)를 겪는다는 거고요.
이번에는 ○○만 만들고 ○○는 빼려고 합니다. ○○는 사람이 결정하도록 두고요. 맞나요?"

## 6. 역제안 — 담당자가 기준을 안 줄 때
담당자가 "있으면 좋고요", "알아서 해 주세요"처럼 미지근하면 질문을 반복하지 말고 내가 정해서 확인받는다.
- 형식: 제안 값 + 그 값으로 생기는 결과 + 나중에 바꿀 수 있음 + "괜찮을까요?"
- 예: "도보 15분은 직선 1.2km로 잡겠습니다. 이렇게 하면 정류장이 먼 직원 300명은 신규 정류장 후보로 따로 보여 드려요. 값은 화면에서 바꿀 수 있습니다. 괜찮을까요?"
- 예: "만석 노선이 문제라면 '최대 인원일 기준'으로 버스 수를 정하겠습니다. 평균 기준보다 버스는 늘지만 못 타는 사람이 없습니다. 이 방향으로 할까요?"
- 동의하면 facts.md의 '기준' 아래에 "역제안 동의"로, 대답이 애매하면 assumptions.md에 '미확인'으로 남긴다. DECISIONS.md 남은 한계에 "담당자 판단으로 조정 가능"을 적는다.
- 대화에 따라 정답이 달라지는 과제가 많다. 무엇을 누구와 정했는지 남긴 기록 자체가 점수다.

## 인터뷰 세션 쓰는 법
담당자 대화 원문은 `work_wiki/interview_log.md` 한 곳에 모은다. 인터뷰 세션은 이 파일을 읽어 사실·가정·질문 목록을 갱신한다. 대화를 세션 채팅창에 붙여 넣지 않는다.
- 실제 시험: 담당자 채팅은 Codex가 읽을 수 없다. 메신저에서 대화를 복사해 interview_log.md 끝에 덧붙인다 (아래 형식).
- 연습 키트: `python tools/ask.py`가 대화를 work_wiki/interview_log.md에 자동으로 덧붙인다.

**interview_log.md 형식** (편집기로 열어 끝에 붙여 넣기)
```
## 10:42
나: 정류장까지 어느 정도 거리면 걸어가세요?
담당자: 걸어서 15분 넘으면 안 타고 차 가져와요.
```
- 시각 제목을 꼭 단다. 사실의 출처와 '어디까지 반영했는지'를 이 시각으로 잡는다.
- 편집기 대신 터미널로 덧붙일 때:
  ```
  cat >> work_wiki/interview_log.md   # 붙여 넣고 Enter, 마지막에 Ctrl+D
  ```

**1) 시작할 때: 질문 목록 만들기**
```
인터뷰 세션이다. README를 읽고 questions.md에 첫 질문 목록을 만들어.
세 질문 순서(현재 방식 → 손실 → 목적 → 숫자·경계 → 빠진 것)마다 질문을 넣고,
README 요구사항 표에 없는 기준, 뜻이 둘로 읽히는 말, 사용자·권한이 정해지지 않은 곳도 질문으로 넣어.
'지금 물을 것' 3개를 보여 줘.
```

**2) 대화할 때마다: 인터뷰 반영**
```
인터뷰 세션이다. 인터뷰 반영.
```
- 세션이 interview_log.md에서 지난번 반영 지점 다음의 새 대화만 읽고, facts·assumptions·questions를 갱신한 뒤 '지금 물을 것' 3개를 보여 준다.
- 답이 애매했던 질문은 역제안 문장으로 바뀌어 '역제안 대기'에 들어간다.

**3) 다른 곳에서 질문거리가 생겼을 때**
```
인터뷰 세션이다. 질문 목록 갱신.
data_profile.md의 이상한 값, 각 세션 기록의 '요청:', rules.json에서 근거가 미확인 가정인 키를 보고 questions.md에 추가해.
```
- 결과를 보여 준 뒤 받은 지적도 interview_log.md에 덧붙이고 "인터뷰 반영".
- 통합 검증이 끝나면 `work_wiki/scenarios.md`의 '담당자 확인 필요' 시나리오로 결과 확인 질문을 만든다: "질문 목록 갱신. scenarios.md의 담당자 확인 필요 시나리오를 결과 확인 질문으로 만들어" → questions.md '결과 확인'의 순서대로 담당자에게 보여 주고 묻는다.
- 인터뷰를 마치기 전: "questions.md의 남은 질문 중 '상'이 있나? 없으면 요약 확인 문장을 만들어" → 요약 확인으로 마무리.

## 화면을 글로 보여 주기 (담당자 채팅은 글만 됨)
결과를 보여 주며 확인받을 때, 인터뷰 세션에 화면 설명문을 만들게 해서 그대로 붙여 넣는다.
```
인터뷰 세션이다. 화면 설명 만들어 UX-S1
```
→ `work_wiki/screen_briefs.md`에 생기는 예:
```
[화면] 검토 목록 — 감사 담당자가 로그인하면 처음 보는 화면
맨 위: "검토 대기 132건 · 위반 의심 3,868만원 · 6월 사용분은 개정 전 규정 적용"
목록 (위험 높은 순, 상위 3줄):
 1) 빨간 배지 "분할 결제" — 영업2팀, 6/18 한정식 수라 3건 합계 82만원, 사전승인 없음 (제10조)
 2) 빨간 배지 "중복 청구" — 구매팀, 7/2 법인카드 승인과 같은 건을 개인 정산 (제3조)
 3) 주황 배지 "금액 불일치" — 영수증 45,000원 / 청구 60,000원 (영수증 금액: AI가 읽음)
줄을 누르면: 근거(조항, 영수증 원문에서 읽은 부분), 버튼 [통과] [보완 요청] [반려하기], 사유 칸
"반려하기"를 누르면 사유 없이는 저장되지 않고, 저장 후 상태가 "반려"로 바뀜
질문: 마감 전에 먼저 보셔야 할 건이 이 순서로 위에 있나요?
```
- 실제 화면에 나온 글자와 숫자만 쓴다. "~할 예정" 같은 계획은 섞지 않는다
- 색은 글자와 함께 쓴다 ("빨간 배지 '반려'"). 코드 값 대신 화면 문구, 개인정보는 가린 그대로
- 한 번에 화면 하나, 질문 하나. 담당자의 반응은 interview_log.md에 덧붙이고 "인터뷰 반영"
- 근거가 될 스크린샷이 없으면 UX 검증 세션(`/tmp/ux-walk`, `/tmp/ux-audit-out`)을 먼저 돌리거나, 세션이 화면 파일과 API 응답으로 확인한 범위만 쓰고 나머지는 '(미확인)'으로 둔다

## 꼬리 질문 만드는 법 (사람용. 인터뷰 세션은 AGENTS.md에 줄여 넣은 같은 기준을 씀)
| 담당자 답 | 다음 질문 |
|---|---|
| 숫자 없이 "많아요", "자주요" | "최근에 실제로 있었던 일 하나만 말씀해 주실래요? 몇 건 정도였어요?" |
| 해결책을 말함 ("이런 기능 있으면") | "그게 생기면 무엇을 하시려고요?" |
| 새 사람·부서가 나옴 ("총무팀이…") | "총무팀은 정확히 뭘 원하세요? 그게 HR 쪽 기준과 부딪히면 누가 정해요?" |
| "알아서 해 주세요" | 역제안 (6절) |
| "있으면 좋고요" | "꼭 있어야 하는 것과 있으면 좋은 것 중 어느 쪽이에요? 없으면 어떤 일이 생겨요?" |
| 데이터와 다른 말 | "자료에서는 ○○로 나오는데, 어느 쪽이 맞아요?" |

## 기록 원칙
- facts.md(사실)와 assumptions.md(가정) 두 파일 안에서 같은 유형 제목으로 정리된다: 현재 방식 / 문제와 손실 / 목적과 사람 / 기준 / 데이터 / 범위 / 권한·보안. 사실에는 출처(인터뷰 시각, 질문)를 단다.
- 빈 유형은 `(아직 없음)`으로 남으니 무엇을 안 물었는지 바로 보인다. facts.md의 '문제와 손실'이 비어 있으면 손실 질문을 아직 안 한 것이다. 문제 정의에는 사실과 데이터가 둘 다 뒷받침하는 것을 쓴다.
- 고르지 않은 문제도 한 줄 남긴다. 예: "작업 속도: 불편은 맞지만 손실 사건 없음 → 제외"
- 데이터에서 본 이상한 숫자는 인터뷰에서 확인한다 ("이 주만 인원이 1.5배인데 왜 그런가요?")
