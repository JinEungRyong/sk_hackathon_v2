# 구현: 세션 운영과 Codex 사용법

## 세션별 쓰는 곳 (AGENTS.md와 같음)
| 세션 | 기록 | 그 밖에 쓰는 곳 | 커밋 접두어 |
|---|---|---|---|
| 인터뷰 | sessions/interview.md | facts.md, assumptions.md, questions.md | `[interview]` |
| 계획 | sessions/plan.md | PLAN·DECISIONS·SOLUTION, work_plan/, work_src/run/ | `[plan]` |
| 구현 `<부분>` | sessions/`<부분>`.md | work_src/`<부분>`/, work_out/`<부분>`.* | `[<부분>]` |
| 검증 | sessions/verify.md | 없음 | `[verify]` |
| 진행상황 정리 | sessions/progress.md (git 제외) | sessions/progress_summary.md (git 제외) | 커밋 안 함 |
- 폴더가 겹치지 않으므로 병렬로 돌려도 서로의 파일을 커밋하지 않는다 (경로 지정 커밋, 07 참고).

## 세션 시작 문장 (복사해서 씀)
**인터뷰** — 02_인터뷰_세질문.md의 '인터뷰 세션 쓰는 법'

**계획** — 04_합의_PLAN.md의 '계획 세션 첫 지시 예'

**구현** (부분마다 탭 하나)
계획 세션이 계획을 마치면 `work_plan/start.md`에 부분마다 지시문을 만들어 준다. 그 블록을 복사해 각 탭에 붙여 넣는다. start.md가 없을 때 쓰는 기본 틀:
```
구현 세션 clean 이다.
work_plan/contract.md의 clean 부분만 만들어. 입력은 contract에 적힌 샘플로 개발해.
contract의 흐름 단계 순서대로 만들고, 단계 이름을 테스트 이름에도 써.
자기 폴더 안의 작은 변경은 바로 하고, 끝나면 바꾼 파일과 테스트 결과를 보여 줘.
형식이나 필드 뜻을 바꿔야 하면 멈추고 요청으로 적어.
완료 기준을 다 통과하면 기록에 '실제 흐름'(단계별 파일·함수·건수, contract와 달라진 점)과 커밋 블록을 남기고, 그 블록 그대로 커밋해.
```

**검증**
```
검증 세션이다. clean을 검증해. (06_검증.md 참고)
```

**진행상황 정리** (중간 점검이나 제출 직전, 검증 탭에서 /new)
```
진행상황 정리 세션이다.
```
- 주제 하나만 다시: `진행상황 정리 세션이다. 운영 조건 값에 대하여`

**재접속 후 이어 가기** (끊긴 세션과 같은 첫 지시)
```
구현 세션 clean 이다. 기록 파일의 마지막 '다음 할 일'부터 이어 가.
```

## 병렬 구현이 깨지는 곳과 막는 법
| 깨지는 곳 | 막는 법 |
|---|---|
| 형식은 같은데 뜻이 다름 (날짜 기준, 단위) | contract.md에 필드 뜻을 기준까지 적고, 샘플에 경계 사례를 넣는다 |
| 커밋에 다른 세션 파일이 섞임 | 폴더 분리 + `git commit -- <내 경로>` |
| 구현 세션이 contract를 고침 | AGENTS.md가 막음. 요청만 남기고 계획 세션에서 내가 정함 |
| 내가 병목 | 작은 변경은 바로 하게, 완료 기준을 테스트로, 승인 대기 탭을 주기적으로 확인 |
| 앞 부분 결과가 늦음 | 뒷 부분은 샘플로 개발, 통합 때 실제 결과로 한 번 더 |

## 규격을 바꿔야 할 때
1. 구현 세션이 기록에 `요청: …`을 남기고 멈춘다
2. 계획 세션에 "clean 요청 보고 contract를 고칠지 정해 줘. 영향받는 부분도 알려 줘"
3. 고치면 계획 세션이 contract·샘플·start.md 커밋 → 계획 세션이 만들어 준 짧은 지시문("contract의 clean이 바뀌었다. 바뀐 점: …")을 영향받는 구현 세션에 붙여 넣기

## 통합 (계획 세션)
```
구현이 다 끝났어. work_src/run/에 전체 실행 명령과 연결 테스트를 만들고,
실제 데이터로 처음부터 끝까지 돌려서 부분마다 입력·출력 건수를 plan.md에 기록해.
운영 조건 하나를 바꿔 다시 돌렸을 때 결과가 바뀌는지도 확인해.
```

## 속도
- 승인 모드는 작업 폴더 안 자동. 승인 대기로 멈춘 탭이 없는지 돌아본다
- 큰 데이터는 통째로 읽지 않게 한다. 요약은 data_profile.md, 개발은 samples/raw/와 부분 샘플로, 전체 실행은 마지막에 한 번
- Codex가 큰 파일을 `cat`하거나 전체를 출력하려 하면 Esc로 멈추고 "살펴보기 코드로 요약만" 또는 "키로 찾아 몇 줄만"이라고 다시 지시
- 세션이 길어지면 /compact. 기록 파일이 있으니 /new로 다시 시작해도 된다
- 같은 실패를 세 번 넘게 반복하면 멈추고 원인부터 묻는다
- 알고리즘은 설명할 수 있는 단순한 방법부터 (회의에서 "왜 이 결과인지" 설명해야 함)

## 자주 쓰는 Codex 기능
- `/plan` 계획만 먼저, `/diff` 변경 확인, `/status` 모델·승인 모드, `/model`, `/compact`, `/new`
- `@파일명`으로 파일 지정, Esc로 중단
- 업데이트 권유가 떠도 업데이트하지 않는다

## AI를 결과물에 넣을 때
- 과제 설명의 '실행 환경'에서 API 제공 여부 확인. 없으면 결과물 안에서 AI 호출하지 않음
- 있으면: 환경변수로만, 호출은 한 부분 안 한 곳에서, 시간 제한, 실패 시 대체 결과, source(rule/ai/fallback) 표시
- AI 결과도 JSON으로 남겨 다음 부분이 코드로 검사한다
