# 전체 워크플로

3시간 과제 기준 예시. 시간이 다르면 비율로 맞춘다.

## 세션 다섯 종류 (터미널 탭)
| 탭 | 세션 | 하는 일 | 언제 |
|---|---|---|---|
| 1 | 인터뷰 | 담당자 대화 정리 → 사실·가정 기록, 질문 목록(questions.md) 갱신, 역제안 | 처음부터 끝까지 |
| 2 | 계획 | PLAN, contract(부분별 입력 → 동작 → 결과), rules.json, 샘플 → 통합·문서 | 합의 후, 통합 때 |
| 3~ | 구현 `<부분>` | 부분 하나씩 병렬 구현 (부분 수만큼 탭) | 계획 확정 후 |
| 마지막 | 검증 | 읽기·실행·대조, 지적만 | 부분이 끝날 때마다 |
| 마지막 | UX 검증 | UX 시나리오를 만들고 따라 하며 화면 검수 (ux-ui-audit-hackathon 스킬) | 서비스 완성 후 |
| 마지막 | 진행상황 정리 | 지금까지 한 일을 '~에 대하여' 주제별로 정리 (progress_summary.md) | 중간 점검, 제출 직전 (검증 탭에서 /new) |

- 세션 시작 문장은 05_구현_Codex.md에 있다.
- 세션마다 `work_wiki/sessions/<세션>.md`에 기록이 쌓인다. 접속이 끊기면 같은 첫 지시로 새로 시작해도 기록을 읽고 이어 간다.

## 시간표
| 단계 | 할 일 | 세션 | 시간 |
|---|---|---|---|
| 0. 자료 읽기 | 나: 과제 설명을 읽고 README의 확정 규칙에 밑줄. 동시에 계획 세션: 큰 데이터 살펴보기와 샘플 추출(04 '첫 지시 1') → data_profile.md의 이상한 값을 인터뷰 질문으로 | 나, 계획 | 0~15분 |
| 1. 인터뷰 | questions.md의 '지금 물을 것' 1번부터 하나씩. 현재 방식 → 손실 → 목적 → 숫자·경계 → 빠진 것 → 요약 확인. 기준을 안 주면 역제안 | 인터뷰 | 15~40분 |
| 2. 계획 | PLAN.md, 부분 나누기(4개 이하), contract.md, rules.json, 샘플. 가정 후보는 인터뷰 세션으로 확인 | 계획 (+인터뷰) | 40~70분 |
| 3. 병렬 구현 | 부분마다 구현 세션 하나. 샘플로 개발, 자기 폴더만 커밋 | 구현 × 부분 수 | 70~125분 |
| 4. 통합 | 실제 데이터로 처음부터 끝까지 실행, 부분마다 건수 확인 | 계획 | 125~140분 |
| 5. 검증 | 부분·산출물 검증 → 담당자에게 보여 주기(인터뷰 세션) → 고치기 | 검증, 구현 | 140~160분 |
| 6. 제출 | 문서 대조, 최종 커밋, 진행상황 정리 읽기, 제출 확정 | 계획, 진행상황 정리 | 160~180분 |

## 원칙
- 처음 10분은 도구에 손대지 않는다. 읽고 생각한다.
- README의 확정 규칙(좌석 수, 시간 조건, "제한 없음" 같은 문장)은 계획 단계에서 바로 rules.json과 테스트로 옮긴다. 늦게 발견하면 고치는 데 오래 걸린다.
- 계획 확정 전에는 구현 세션을 열지 않는다. 규격이 흔들리면 병렬 작업이 전부 다시 하게 된다.
- 첫 동작 버전(샘플로 처음부터 끝까지)은 전체 시간의 절반 안에.
- AI가 구현하는 동안 놀지 않는다: 인터뷰 세션으로 담당자 확인, 검증 세션 돌리기, 원본 대조.
- 승인 대기로 멈춘 세션이 없는지 탭을 돌며 확인한다.
- 인터뷰와 데이터가 다르면 인터뷰·계획으로 돌아간다.

## 병렬로 할지, 하나로 할지
- 병렬: 부분이 3개 이상이고 데이터가 크거나 부분마다 일이 무거울 때
- 구현 세션 하나로 순서대로: 부분이 2개 이하, 데이터가 작음, 남은 시간이 짧음
- 세션 수 상한은 두지 않는다. 다만 세션이 늘수록 승인 대기 확인, 토큰 사용량, 커밋 충돌(`index.lock`), 끊긴 뒤 복구할 탭이 함께 는다.

## 접속이 끊길 때
- 화면이 끊겨도 VM 안의 Codex는 계속 도는 경우가 많다. 끊기기 쉬우면 구현 세션에 contract 한 부분을 통째로 맡겨 두고 재접속한다.
- 재접속하면 `git log --oneline | head`와 각 `work_wiki/sessions/*.md`의 마지막 '다음 할 일'로 상태를 파악한다.

## 시작 직후 할 일
1. 작업 키트 복사 (07_git_명령어.md의 '시작할 때')
2. 첫 커밋: `add: 하네스 구축`
3. 과제 설명의 '실행 환경'에서 결과물 안에 쓸 AI API가 제공되는지 확인

## 과제 유형별 조정
- 데이터가 아주 많다: 0단계를 두 배로. 계획 세션의 data_profile.md를 내가 직접 읽고 해석한다. 원본을 Codex가 통째로 읽으려 하면 Esc로 멈추고 "살펴보기 코드로 요약만"이라고 다시 시킨다.
- 담당자가 미지근하다(기준을 안 줌): 역제안으로 정하고 가정으로 기록, 한계에 "담당자 판단으로 조정 가능"을 적는다. 02 참고.
- 실무자가 없다: 세 질문을 과제 설명과 자료에 던지고, 답이 없는 부분은 assumptions.md에 가정으로.

## 하나로 줄이면
문제를 한 문장으로 다시 정의하고, 사실·가정·운영 조건을 나누고, 부분마다 입력과 결과를 고정해서 병렬로 만든다.
