# G. 업무 화면 (해커톤·FDE 결과물) — 항상 읽음

담당자가 이 화면으로 **결정**을 내리고, 그 결정을 **회의나 직원에게 설명**해야 하는 화면을 기준으로 본다.
일반 UI 품질보다 "잘못 판단하게 만드는가", "근거를 설명할 수 없게 만드는가"를 먼저 본다.

## 1. 첫 화면과 순서
- 사용자의 핵심 결정에 필요한 것이 첫 화면 맨 위에 있는가? (급한 건, 위반 금액 큰 건, 부족 구간, 과밀 노선 등)
- 목록의 정렬 기준이 화면에 적혀 있는가? ("위험 높은 순", "금액 큰 순")
- 목록 위에 전체 건수와 필터 결과 건수가 보이는가?
- 성공 기준(PLAN.md)과 관련된 숫자가 첫 화면에서 보이는가? (예: 과밀 노선 18 → 0, 포기율, 위반 금액)

## 2. 숫자와 근거
- 숫자에 단위·기준 시점·계산 근거가 함께 있는가? (예: "부족 12명 — 월 10:30, 필요 80 / 배치 68")
- 판정 결과 옆에 근거가 있는가? (어떤 규칙·조항, 어떤 기준 값, 원본에서 무엇을 읽었는지)
- 규칙으로 나온 결과, AI로 나온 결과, 확인이 필요한 결과가 라벨로 구분되는가?
- 기준 값(운영 조건)이 지금 무엇으로 적용됐는지 화면 어딘가에 보이는가?
- 담당자가 "왜 이렇게 나왔냐"는 질문에 화면만 보고 답할 수 있는가? 못 하면 High.

## 3. 상태 표시
- 상태가 코드 값(`needs_review`, `PENDING`, `true/false`, `null`, `NaN`, `undefined`)으로 나오지 않는가? 나오면 High.
- 상태 문구가 contract.md 상태 표의 '화면 문구'와 같은가?
- 상태를 색만으로 구분하지 않고 글자 라벨이 함께 있는가?
- 같은 상태가 화면마다 다른 말로 나오지 않는가? ("반려" / "거절" / "rejected")

## 4. 비어 있음·오류·실패
- 빈 목록, 데이터 오류, AI 응답 실패, 권한 없음, 서버 오류마다 무엇이 문제인지와 다음에 할 일을 한 줄로 알려 주는가?
- AI가 실패해도 화면이 깨지지 않고 '확인 필요'나 대체 결과로 보이는가?
- 처리에서 버려지거나 연결되지 않은 건수가 숨겨지지 않고 보이는가? (예: "좌표 오류 9명, 확인 필요")

## 5. 결정과 다시 생성
- 결정 버튼(통과·반려·확정 등)의 문구가 결과를 말하는가? ("확인" 대신 "반려하기")
- 되돌리기 어려운 결정 전에 확인이 있거나, 결정 후 되돌릴 수 있는가?
- 결정 뒤 성공·실패가 보이고, 중복 클릭이 막히는가?
- 결정 사유를 남기는 칸이 있는가? (결정 기록이 요구된 과제일 때)
- 기준 값을 바꾸고 다시 생성할 때, 진행 중 표시와 끝난 뒤 "무엇이 바뀌었는지"(전후 비교, 바뀐 건수)가 보이는가?
- 다시 생성한 뒤 사람이 내린 결정이 그대로 남아 있는가? 사라지면 Critical.

## 6. 권한과 개인정보 (보이면 Critical)
- 사용자 계정으로 운영자 화면·기능에 들어가지는가?
- 주소나 요청의 식별자(사번 등)를 바꾸면 다른 사람의 데이터가 보이는가?
- 화면·다운로드에 전체 카드번호, 개인 좌표·주소, 전화번호, 휴무 사유 같은 민감 정보가 그대로 나오는가?
- 화면 소스나 응답 JSON에 화면에 안 보이는 민감 필드가 실려 오는가? (개발자 도구로 보이는 것도 노출)

## 7. 표기와 용어
- 한국어 업무 용어를 쓰고 시스템 필드명을 노출하지 않는가?
- 날짜·시간·금액·인원 형식이 화면 전체에서 같은가? (예: 2026-11-16(월), 12,000원, 45명)
- 표에서 숫자는 오른쪽 정렬, 글자는 왼쪽 정렬인가? (Low)
- 긴 표는 머리줄이 보이게 하거나 나눠서 보여 주는가? (Medium)

## 8. 실행 환경
- 외부 CDN·웹 폰트에 의존해서, 인터넷이 막힌 환경에서 화면이 깨지지 않는가? 깨지면 High.
- 서버를 `0.0.0.0`에 띄웠을 때 다른 주소로 접속해도 화면이 정상인가? (절대 주소 `localhost` 하드코딩 확인)

## 판정 규칙
- 이 파일의 항목은 과제와 담당자 요구에 해당할 때만 Issue로 만든다. 예: 결정 기록이 요구되지 않은 과제에서 사유 칸이 없다고 지적하지 않는다.
- 권한·개인정보 문제는 UX 보고서에 쓰되, 보안 문제이기도 하므로 검증 세션(verify.md)에도 알리라고 보고서에 적는다.
