# UX/UI Audit (해커톤용)

완성된 서비스에서 **UX 시나리오를 먼저 만들고 그대로 따라 해 보면서**, 실제 사용자 작업을 방해하는 문제를 찾아 근거와 심각도에 따라 정리한다.
목표는 문제 개수를 늘리는 것이 아니라, 남은 시간 안에 고칠 가치가 있는 문제를 같은 기준으로 고르는 것이다.
최종 판단은 사람이 한다.

## 0. 해커톤 모드 (기본)

1. **보고만 한다.** 이 스킬을 쓰는 세션은 결과물 코드·문서를 고치지 않는다. 보고서(`work_wiki/ux_audit.md`)와 자기 세션 기록만 쓴다. 고치는 일은 화면을 맡은 구현 세션이 한다. 사용자가 명시적으로 "직접 고쳐"라고 할 때만 5절의 '직접 고치는 경우'를 따른다.
2. **저장소를 더럽히지 않는다.** Playwright 설치, 측정 결과(`report.json`), 스크린샷, 로그인 상태 파일은 모두 `/tmp` 아래에 둔다. 저장소에서 `npm i`를 실행하지 않는다.
3. **핵심 작업은 과제 문서에서 가져온다.** README의 페르소나·기능, `PLAN.md`의 사용자·성공 기준, `work_plan/contract.md`의 화면·상태 표, `work_wiki/scenarios.md`의 통합 검증 시나리오를 먼저 읽고, 화면마다 핵심 작업을 한 줄로 적는다.
4. **업무 화면 기준을 항상 읽는다.** `references/ops-screen.md`는 범위와 상관없이 매번 읽는다.
5. **로그인 뒤 화면을 실측한다.** 로그인이 필요한 화면은 `scripts/login.mjs`로 로그인 상태 파일을 만든 뒤 `audit.mjs --storage-state`로 측정한다. 시험용 계정은 `SOLUTION.md` 또는 시드 파일에서 찾고, 계정 값은 보고서에 쓰지 않는다.
6. **뷰포트**: PC 화면만 본다. 기본 `1440x900`. 모바일·터치·반응형은 검수 대상이 아니다.
7. **시간 상자**: 시나리오 작성 5분, 따라 하기·측정·보고 15분. 시나리오는 5~8개, Issue는 최대 10개. Critical·High를 먼저 찾고 나머지는 '남은 개선' 한 줄씩.
8. **시나리오가 먼저다.** Issue는 시나리오를 따라 하다 막히거나 늦어진 곳에서 찾는다. 시나리오와 관계없는 화면 구석의 문제는 '남은 개선'으로 내린다.

## 1. 검수 원칙

1. 먼저 화면의 목적과 핵심 사용자 작업을 파악한다.
2. 핵심 작업을 막거나 늦추는 문제를 먼저 다룬다.
3. 취향 차이는 Issue로 만들지 않는다.
4. 확인한 사실과 추측을 구분해서 쓴다.
5. 원인이 같은 문제는 하나의 Issue로 묶는다 (공통 컴포넌트·공통 CSS 단위로).
6. 수정안은 기존 화면 구조와 스타일을 최대한 유지한다. 새 라이브러리·외부 CDN·빌드 단계를 제안하지 않는다.
7. 직접 확인할 수 없는 동작은 `검증 필요`로 남긴다.
8. 체크리스트를 채우려고 문제를 만들어내지 않는다.
9. 문제 개수보다 사용자 영향과 수정 효과를 우선한다.

## 2. 근거 기준

Issue를 `확정`하려면 아래 중 하나 이상의 근거가 있어야 한다.

- 화면에서 직접 관찰한 내용 (스크린샷 경로)
- 코드 (파일:줄, CSS 값)
- 실행 결과, 실제 측정값 (`audit.mjs` 결과)
- 과제 문서·담당자 사실 (`facts.md`, `contract.md`의 화면 문구)

스크린샷만으로는 다음을 단정하지 않는다: 키보드 Focus 동작, Hover/Press/Loading 피드백, 뒤로가기, 스크린리더 동작, API/네트워크 상태, 정확한 대비율, 정확한 Font Size.
이런 항목은 `판정: 검증 필요`로 쓰고, 무엇을 확인하면 확정되는지 적는다.

## 3. 심각도

| 심각도 | 기준 | 업무 서비스 예 |
|---|---|---|
| **Critical** | 핵심 작업을 끝낼 수 없음, 데이터 손실, 권한·개인정보 노출 | 결정 버튼이 동작하지 않음, 다른 사용자 데이터나 카드번호·개인 좌표가 보임, 다시 생성하면 사람의 결정이 사라짐 |
| **High** | 핵심 흐름에 큰 장애, 잘못 판단하게 만듦 | 급한 항목이 묻힘, 숫자에 근거가 없어 담당자가 설명 못 함, 상태가 코드 값으로 나옴, 오류·빈 상태 안내 없음 |
| **Medium** | 사용은 되지만 반복적으로 불편하거나 이해가 늦어짐 | 정렬 기준 안 보임, 건수 표시 없음, 날짜·금액 형식 제각각 |
| **Low** | 주요 작업에 영향이 적은 품질 개선 | 간격 리듬, 폰트 크기 종류 과다 |

눈에 잘 띈다는 이유만으로 심각도를 올리지 않는다.

## 5. 절차

### 5-1. UX 시나리오 만들기 (검수 전에 먼저)
UX 시나리오는 "어떤 사용자가, 어떤 화면에서 시작해, 무엇을 끝내야 하는가"다. 기능이 동작하는지(통합 검증)보다 **사용자가 헤매지 않고, 잘못 판단하지 않고 끝낼 수 있는지**를 본다.

시나리오를 찾는 곳:
- README 페르소나별 기능: 역할마다 가장 자주 하는 일 하나 이상
- `facts.md`의 '문제와 손실'·'목적과 사람': 손실마다 "담당자가 이 화면으로 그 손실을 막는 장면" 하나 (예: 분할 결제 묶음을 찾아 반려하기)
- `contract.md` 상태 표: 사람이 상태를 바꾸는 결정 경로 (예: 검토 대기 → 반려 + 사유)
- 기준 값을 바꿔 다시 생성하고, 무엇이 바뀌었는지 확인하는 장면
- 빈 목록, 오류, AI 실패 화면을 만났을 때 다음에 할 일을 알 수 있는지
- 사용자 역할로 운영자 화면이나 남의 데이터에 접근하는 장면 (막혀야 성공)
- `work_wiki/scenarios.md`(통합 검증)에 화면 관련 시나리오가 있으면 번호를 함께 적어 겹치지 않게 한다

보고서 맨 앞에 표로 쓴다:
```
| 번호 | 사용자 | 하려는 일 | 시작 화면 | 단계 (요약) | 성공 조건 | 지켜볼 것 |
| UX-S1 | 감사 담당자 | 분할 결제 묶음을 찾아 반려한다 | 검토 목록 | 목록 → 묶음 열기 → 근거 확인 → 반려 + 사유 | 3번 안의 클릭으로 묶음 합계와 조항이 보이고 반려가 저장됨 | 묶음이 한 줄로 보이는가, 근거가 보이는가 |
```
- '성공 조건'은 확인할 수 있게 쓴다 (화면에 보여야 할 글자, 저장 결과, 클릭 수).
- '지켜볼 것'은 `references/ops-screen.md`에서 그 시나리오에 해당하는 항목을 고른다.

### 5-2. 준비
1. **측정 도구** (처음 한 번, 저장소 밖):
   ```bash
   bash <skill-dir>/scripts/setup_playwright.sh        # /tmp/uxpw 에 설치. 이미 있으면 건너뜀
   ```
   설치가 막히면(네트워크 제한) 측정과 스크린샷 없이 시나리오를 코드로 따라가며 정적 검토로 진행하고, 보고서에 '실측 미실시'라고 적는다.
2. **서버 실행**: `SOLUTION.md`의 실행 명령으로 띄운다. 실행 중 생기는 DB·파일은 `/tmp`를 쓰도록 환경변수나 작업 사본으로 띄운다.
3. **로그인 상태 만들기** (역할마다):
   ```bash
   cd /tmp/uxpw && node <skill-dir>/scripts/login.mjs --url http://localhost:3000/login \
     --user <시험용 아이디> --pass <시험용 비밀번호> --out /tmp/ux-state-admin.json
   ```
   입력창을 못 찾으면 `--user-field`, `--pass-field`, `--submit`에 선택자를 준다.

### 5-3. 시나리오 따라 하기
시나리오마다 단계 파일(`/tmp/ux-scenarios/UX-S1.json`)을 만들고 실행한다. 형식은 `scripts/walk.mjs` 맨 위 주석을 본다.
```bash
cd /tmp/uxpw && node <skill-dir>/scripts/walk.mjs /tmp/ux-scenarios/UX-S1.json --out /tmp/ux-walk
```
- 결과: 끝까지 진행 / N단계에서 막힘, 단계별 걸린 시간, 스크린샷, 콘솔·HTTP 오류
- 막힌 단계와 스크린샷을 직접 보고 왜 막혔는지 판단한다 (버튼을 못 찾음, 문구가 결과를 말하지 않음, 근거가 안 보임, 오류 안내 없음 등)
- 시나리오의 '성공 조건'은 `expectText`, `expectNoText`(예: 코드 값 `needs_review`, 카드번호 앞자리), `expectUrl`로 적는다
- 화면을 따라 할 수 없는 시나리오(예: 시간이 걸리는 다시 생성)는 코드와 API 응답으로 확인하고 '검증 필요' 여부를 적는다

### 5-4. 화면 측정
시나리오에서 거친 화면을 측정한다.
```bash
cd /tmp/uxpw && node <skill-dir>/scripts/audit.mjs http://localhost:3000/admin http://localhost:3000/admin/items/1 \
  --storage-state /tmp/ux-state-admin.json --viewport 1440x900 --out /tmp/ux-audit-out/admin
```
측정값은 근거 자료이며 그대로 Issue가 되지 않는다. 시나리오와 관련된 것만 골라 Issue의 근거로 쓴다.

### 5-5. 보고와 넘기기
1. 6절 형식으로 `work_wiki/ux_audit.md`에 쓴다. 시나리오 표와 결과가 맨 앞, Issue는 심각도 높은 순, 각 Issue에 관련 시나리오 번호.
2. 보고서 끝에 '구현 세션에 넘길 지시문'을 쓴다. 고칠 Issue는 사용자가 고른다.
3. 구현 세션이 고친 뒤 **같은 시나리오 파일로 다시 따라 하고** 같은 측정을 다시 돌려, 시나리오 결과와 Issue의 `재검증` 칸을 채운다 (`수정 전 → 후`).

### 직접 고치는 경우 (사용자가 명시했을 때만)
기존 클래스·공통 CSS를 고쳐 여러 화면을 한 번에 해결하는 쪽을 우선한다. 임의 값을 새로 흩뿌리지 않는다. 화면 파일만 고치고 API·DB·권한 코드는 건드리지 않는다. 고친 뒤 5-5의 재검증과 기존 테스트를 돌린다.

## 6. 출력 형식 (`work_wiki/ux_audit.md`)

````markdown
# UX/UI 검수 (HH:MM 기준)
## 요약
- 대상: <역할별 화면 목록>, 뷰포트: 1440×900, 실측: 실시/미실시
- 시나리오 6개: 끝까지 진행 4 · 막힘 1 · 검증 필요 1
- Critical 0 · High 2 · Medium 3 · Low 1
- 먼저 고칠 것: UX-01, UX-02, UX-03

## UX 시나리오
| 번호 | 사용자 | 하려는 일 | 시작 화면 | 단계 (요약) | 성공 조건 | 지켜볼 것 | 결과 | 관련 Issue |
|---|---|---|---|---|---|---|---|---|
| UX-S1 | … | … | … | … | … | … | 끝까지 진행 / N단계에서 막힘 / 검증 필요 | UX-01 |

### UX-01 — <문제를 한 줄로>
- 심각도: High · 판정: 확정 | 검증 필요 · 영역: 업무 화면 / Hierarchy / Typography … · 시나리오: UX-S1
- 위치: <화면, 파일:줄 또는 선택자>
- 근거: <시나리오 단계 결과, 관찰·코드·측정값. 스크린샷 경로. 수치가 있으면 수치로>
- 영향: <어떤 사용자가 어떤 작업에서 무엇을 못 하거나 잘못 판단하나>
- 개선: <구체적 수정안. 기존 클래스·파일 이름 포함>
- 재검증: <고친 뒤 무엇을 확인하면 되는지>
- 신뢰도: 높음 | 중간 | 낮음

## 남은 개선 (시간이 남으면)
- <한 줄씩>

## 구현 세션에 넘길 지시문
```
구현 세션 <화면 부분> 이다. work_wiki/ux_audit.md의 UX-01, UX-02를 반영해.
화면 파일만 고치고 API·DB·로그인·권한 코드는 그대로 둔다. 외부 CDN·새 패키지는 쓰지 않는다.
고친 뒤 기존 테스트와 권한 테스트를 다시 돌리고, 기록에 Issue별 수정 내용을 남겨.
```
````

재검증 후에는 다음을 덧붙인다:

```markdown
## 반영 결과
| Issue | 수정 내용 | 수정 전 → 후 |
|---|---|---|
| UX-02 | 상태 배지에 글자 라벨 추가 | 색만 → 색+라벨 |
```
