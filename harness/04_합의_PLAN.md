# 합의와 계획 (계획 세션)

## 합의할 항목
1. 문제 이해 확인 (요약 문장에 "맞아요"를 받음)
2. 병목 위치와 왜 생기는지
3. 성공 기준: 숫자, 현재값 → 목표값, 측정 방법
4. 만들 것(산출물 3~5개) / 안 만들 것
5. 제약: 환경, 보안, 사람이 결정할 것
6. 운영 조건과 가정값: 실무자 답이나 역제안으로 정한 기준
7. AI 역할: AI가 할 일과 안 할 일 ("판정은 규칙, AI는 초안 문장만, 발송은 사람")

## 세 가지를 나눠 둔다
| 파일 | 담는 것 | 예 | 쓰는 세션 |
|---|---|---|---|
| `work_wiki/facts.md` | 인터뷰에서 확인한 사실 (안에서 유형별 제목) | 기준: 도보 15분 넘으면 안 탄다 (인터뷰 10:42) | 인터뷰 |
| `work_wiki/assumptions.md` | 담당자가 안 정해 줘서 내가 정한 것 | 직선거리를 실제 거리로 본다 \| 지도 금지 \| 강을 건너는 곳은 과소평가 \| 미확인 | 인터뷰 |
| `work_plan/rules.json` | 바꿀 수 있는 운영 조건 (값 + 근거) | `"max_walk_km": {"value": 1.2, "근거": "사실: 도보 15분"}` | 계획 |
- 후속 질문에서 "그 값은 누가 정했나"를 물으면 이 세 파일로 바로 답한다.
- 계획 세션이 근거 없는 값을 만나면 plan.md에 `요청: 가정 후보`로 남기고, 인터뷰 세션이 역제안 문장으로 바꾼다.

## 부분 나누기 (코드 → JSON → 코드)
- 결과물을 3~4개 부분으로 자른다. 자르는 곳 = 결과를 파일로 남겨 두면 확인하기 좋은 곳.
- 흔한 모양: 정리(원본 → 깨끗한 JSON) → 계산·판정 → 결과 묶음 → 화면·DB
- 계산(판정) 부분과 화면·DB 부분을 반드시 나눈다. 계산은 HTTP·DB 없이 테스트할 수 있어야 한다. (후속 질문에 "입력·계산·저장의 경계를 어떻게 나눴나"가 나온다)
- 운영 조건을 화면에서 바꿔 다시 생성해야 하면: 화면 부분이 새 운영 조건 파일을 저장하고, 앞 부분들을 그 파일 경로로 다시 실행한다.

## contract.md 맨 위: 전체 흐름 예시 (통근버스형)
```
## 전체 흐름
data/schedule.csv, residences.csv, stops.csv
  → [clean]  근무표·거주지 정리          → clean.jsonl, clean.summary.json
  → [demand] 직원을 정류장에 배정, 교대·정류장별 탑승 인원 → demand.json
  → [route]  좌석·탑승 시간 안에서 노선 생성, 시각 계산 → route.json
  → [web]    DB 적재, 운영자·구성원 화면, 규칙 저장 → 화면·DB
- 운영 조건이 바뀌면: work_codes → clean부터 / max_walk_km, demand_basis → demand부터 / seats, max_ride_min, speed_kmh → route부터
- 화면에서 규칙을 저장하면: web이 새 규칙 파일을 만들고 바뀐 키에 맞는 부분부터 다시 실행 → route.json 다시 적재
```
- 이 덩어리 하나로 "무엇이 어디로 흘러가는지"와 "무엇을 바꾸면 어디부터 다시 도는지"가 보여야 한다.
- 후속 질문의 "구조를 설명하라", "HTTP·계산·DB 경계는?"에 이 덩어리를 그대로 말하면 된다.

## contract.md 한 부분 예시
```
## clean
- 목적: 손으로 입력한 근무표의 표기 차이 때문에 탑승 인원이 틀리지 않게 한다 (facts.md 데이터: 휴무 표기 섞임)
- 입력: data/schedule.csv (근무일, 사번, 근무지, 근무코드)
- 쓰는 운영 조건: work_codes
- 흐름:
    1. 읽기: schedule.csv 행 → 원본 행 목록 (입력 행 수 기록)
    2. 정리: 근무코드 앞뒤 공백 제거, 대문자로 → 정리된 코드 ("d" → "D", "OFF " → "OFF")
    3. 판정: work_codes에 있으면 근무, 그 밖의 코드는 휴무, 빈 코드는 '확인 필요' (버리지 않음)
    4. 저장: 근무 행 → clean.jsonl / 건수와 확인 필요 이유 → clean.summary.json
- 결과: work_out/clean.jsonl
    work_date = 근무를 시작한 날 (야간조는 다음 날 아침 퇴근)
    site = 그날 실제로 일한 근무지 (지원 근무 반영)
    shift = D/E/N 중 하나
  + work_out/clean.summary.json: 입력 행 수, 근무 행 수, 휴무 행 수, 확인 필요 행 수와 이유
- 경계 사례: "d", "N ", "휴무", "OFF ", 빈 값, 지원 근무
- 샘플: work_plan/samples/clean.jsonl (12행)
- 완료 기준: 경계 사례 테스트 통과, 결과가 샘플과 같은 키·타입, 입력 = 근무 + 휴무 + 확인 필요
- 실행 명령: (계획 세션이 정함)
```

## 상태 표 예시 (상태 필드가 있을 때, contract에 둠)
```
### 청구 처리 상태 (claim.status)
| 값 | 뜻 | 누가·무엇이 바꾸나 | 다음 상태 | 화면 문구 |
|---|---|---|---|---|
| clear | 규칙상 문제 없음 | 판정(check) | needs_review (기준 값이 바뀌어 다시 판정할 때) | 문제 없음 |
| needs_review | 위반 의심, 사람 검토 전 | 판정(check) | approved, supplement, rejected | 검토 대기 |
| supplement | 보완 요청 | 감사 담당자 | needs_review (직원 재제출 시) | 보완 요청 |
| approved | 통과 | 감사 담당자 | (끝) | 통과 |
| rejected | 반려 | 감사 담당자 | (끝) | 반려 |
흐름: 판정 → clear 또는 needs_review → (사람) approved / supplement / rejected, supplement → 재제출 → needs_review
다시 판정할 때: 사람이 정한 approved·supplement·rejected는 유지, clear·needs_review만 다시 계산
```
- 상태 이름은 코드용 영어 값과 화면 문구를 나눠 적는다. 화면에 `needs_review` 같은 코드 값이 그대로 나오지 않게.
- '다시 판정할 때' 줄이 가장 중요하다. 이게 없으면 기준 값을 바꿀 때 사람의 결정이 지워진다.

## 샘플 만들기
- 샘플은 앞 부분의 결과 = 뒷 부분의 입력이다. 그래서 뒷 부분이 앞 부분을 기다리지 않는다.
- 10~30행. 정상 몇 개 + 경계 사례를 모두 넣는다.
- 계획 세션에 "앞 부분 샘플이 뒷 부분 입력 형식과 같은지 직접 확인해"라고 시킨다.

## 계획 세션 첫 지시 1: 큰 데이터 살펴보기 (시작 직후, 인터뷰와 동시에)
```
계획 세션이다. 먼저 제공 데이터를 살펴봐. 원본 파일은 통째로 열거나 출력하지 마.
살펴보기 코드를 work_src/run/에 만들어서 파일마다 크기, 행 수, 열 이름, 앞 5행과 무작위 5행(시드 고정),
열별 빈 값 수와 값 종류(코드 같은 열은 값별 건수, 숫자·날짜는 최소·최대)를 work_plan/data_profile.md에 써.
표기 차이, 범위 밖 값, 중복 키, 특정 날짜·그룹만 튀는 건수가 있으면 따로 모아 줘.
그다음 원본마다 앞부분·무작위·이상한 값 행을 섞어 20~50행을 work_plan/samples/raw/에 뽑고 기준을 적어.
끝나면 이상한 값과 담당자에게 물어볼 것만 짧게 보고해.
```
- 보고받은 이상한 값은 인터뷰 질문이 된다. 예: "10월 둘째 주만 인원이 1.5배인데 왜 그런가요?"
- data_profile.md는 내가 직접 읽는다. 데이터 해석은 내가 한다.

## 계획 세션 첫 지시 2: 계획 (인터뷰 후)
```
계획 세션이다.
facts.md, assumptions.md, README, data_profile.md를 보고
1) PLAN.md 초안 2) 부분 나누기(4개 이하)를 먼저 보여 줘.
부분 나누기는 '전체 흐름' 한 덩어리와, 부분마다 입력 → 흐름(3~6단계) → 결과 요약으로 보여 줘.
README의 확정 규칙은 전부 rules.json 후보로 뽑아. 내가 확인하면 contract.md, rules.json, 샘플을 만들어.
```
- 흐름 요약을 보고 확인할 것: 계산이 화면·DB와 떨어져 있나, 버리는 데이터가 어느 단계에서 몇 건 나오나, 운영 조건 키가 어느 단계에서 쓰이나.
- 흐름이 이상하면 이 단계에서 고친다. 구현 세션을 연 뒤에 고치면 모두 다시 해야 한다.

## 합의 후 할 일
- `[plan]` 커밋: PLAN.md, work_plan/, .gitignore(work_out/), AGENTS.md '과제별 규칙'
  ```
  - 결과물 형태: (예: 웹 화면 운영자 + 구성원, 0.0.0.0:3000, Docker)
  - 데이터·보안: (예: 개인 좌표는 화면·로그·AI에 노출 금지)
  - AI 사용: (예: 제공된 환경변수만, 변경 요약 문장만, 실패 시 템플릿)
  - 사람이 결정할 것: (예: 신규 정류장 설치는 후보만 표시)
  ```
- 계획 세션에 "구현 세션 지시문 만들어"라고 하면 `work_plan/start.md`에 부분마다 복사용 지시문과 동시에 열 순서가 나온다 (AGENTS.md에 형식이 있음)
- start.md를 훑어보고(입력 샘플 경로, 주의할 경계 사례, 완료 기준이 맞는지) 구현 세션 탭에 하나씩 붙여 넣는다 (05)

## 산출물 정하는 요령
- 산출물 = 사용자가 받거나 보는 것 하나 (화면 영역, 생성 파일, 문서). 3~5개
- 첫 산출물은 "진짜 문제"를 직접 해결하는 것
- 산출물 표의 '만드는 부분'으로 산출물과 부분을 잇는다
